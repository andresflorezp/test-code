GitHub — Estándares de la Organización

Documento de consulta, no de lectura obligatoria. Para el trabajo diario usa la Guía Rápida. Aquí está el "por qué" y las reglas que aplican a nivel de organización.

Owner: Equipo DevOps – Plataforma · Versión: 1.0 · Actualizado: (fecha)

1. Estructura organizacional

Enterprise (Banamex)
└── Organization: banamex-<dominio>
    ├── Teams (developers, devops, qa, owners)
    └── Repositories

Regla de oro: los permisos se otorgan a Teams, nunca a personas.

Cuando alguien entra o sale del proyecto se toca un solo lugar. Con accesos individuales el offboarding es imposible de auditar.

Team Permiso
<dominio>-owners Admin
<dominio>-devops Maintain
<dominio>-developers Write
<dominio>-qa Write o Triage
<dominio>-readonly Read

2. Permisos

Nivel Puede Perfil
Read Ver, clonar, comentar Stakeholders, auditoría
Triage + gestionar issues y PRs (sin escribir código) QA, soporte
Write + push, crear PRs, aprobar Desarrolladores
Maintain + configurar el repo y sus secrets Tech leads, DevOps
Admin Control total (borrar, cambiar visibilidad, accesos) Plataforma

Principios:

  • Mínimo privilegio: el permiso más bajo que permita trabajar.
  • Admin es excepcional — máximo 2–3 personas por organización.
  • Toda solicitud de acceso pasa por Jira.
  • Revisión trimestral de accesos.

Obligatorio en toda cuenta: 2FA habilitado, acceso vía SSO corporativo, tokens fine-grained con expiración máxima de 90 días. Prohibido compartir credenciales.

3. Nombres de repositorios

<dominio>-<producto>-<tipo>

Todo en minúsculas, kebab-case, en inglés, máximo 50 caracteres.

Sufijo Para
-api Servicios expuestos
-service Microservicios internos
-web / -mobile Aplicaciones
-lib Librerías reutilizables
-infra Infraestructura como código
-docs Documentación
-tools Utilidades internas

✅ payments-transfers-api · cards-fraud-service · core-logging-lib ❌ API_Pagos_Nueva · proyecto-juan · backend2 · repo-v2-final

Nunca: guiones bajos, mayúsculas, nombres de personas, sufijos de versión (-v2, -new, -old).

4. Creación de repositorios

Ningún repositorio se crea manualmente desde GitHub. Todo nace de un ticket de Jira para asegurar trazabilidad y aplicación automática de estándares.

Flujo

Solicitud en Jira → Aprobación Tech Lead → Creación automatizada → Entrega

Datos obligatorios del ticket

  • Nombre propuesto (según sección 3)
  • Dominio dueño + Tech Lead aprobador
  • Descripción funcional (2–3 líneas)
  • Tipo de repo y stack principal
  • Teams que requieren acceso y nivel
  • ¿Maneja datos sensibles o regulados?

5. Estrategia de ramas

Trunk-based con ramas de corta duración. main es la única fuente de verdad.

main ────●────────●────────●────────●──────▶
          \      /          \      /
           ●────●            ●────●
       feature/PAY-1234   bugfix/PAY-1235
Rama Duración Nace de Vuelve a
main Permanente — —
feature/* bugfix/* Máx. 5 días hábiles main main
hotfix/* Horas main main

Hotfix: nace de main, revisión acelerada (1 aprobador + Tech Lead), merge + tag patch.

Nota: si el dominio trabaja con ventanas de despliegue fijas o certificación previa, aplica el modelo con rama develop. Coordinar con el Tech Lead.

6. Protección de ramas

Se aplica vía Rulesets a nivel de organización — ningún repo queda sin protección.

Sobre main:

Regla Valor
PR obligatorio antes de merge ✅
Aprobaciones requeridas 2
Descartar aprobaciones al subir commits nuevos ✅
Revisión de Code Owners ✅
Status checks (build, tests, SAST, lint) ✅
Rama actualizada con main ✅
Conversaciones resueltas ✅
Historial lineal ✅
Bloquear force push y borrado ✅
Aplica también a administradores ✅

Estrategia de merge: Squash and merge por defecto. Rebase caso a caso. Merge commit deshabilitado.

7. Labels estándar

Todos los repos se crean con el mismo set. Filtrado y reportería homogénea.

Grupo Labels
Tipo type: feature · type: bug · type: hotfix · type: refactor · type: docs · type: chore
Prioridad priority: critical · high · medium · low
Estado status: wip · ready for review · changes requested · blocked
Área area: backend · frontend · infra · ci-cd · security · database
Especiales breaking change · needs discussion · dependencies

Reglas: todo PR lleva mínimo un type: y un priority:. Los labels no se crean ad hoc por repo — se solicitan vía Jira para agregarlos al set de la organización.

(Colores hex definidos en el script de aprovisionamiento.)

8. Integración con Jira

Cuando la clave de Jira aparece en la rama, el commit y el título del PR, Jira muestra automáticamente ramas, commits, estado del PR y despliegue. Esto elimina el reporte manual de avance.

9. Seguridad

Nunca al repositorio

Contraseñas, tokens, API keys, certificados privados, .env con valores reales, cadenas de conexión, datos de clientes reales, dumps de BD productiva, llaves SSH privadas.

⚠️ Borrar un secreto en un commit posterior no lo elimina — queda en el historial. Si se sube: rotar la credencial de inmediato y reportar a Seguridad.

Dónde van los secretos

Contexto Mecanismo
Local .env en .gitignore + .env.example sin valores
CI/CD GitHub Secrets (org o repo)
Runtime Gestor de secretos corporativo

Controles habilitados por defecto

Secret Scanning con Push Protection · Dependabot (alertas y updates) · Code Scanning (SAST) · Audit Log

10. Versionamiento

SemVer: MAJOR.MINOR.PATCH → tag v2.4.1

  • MAJOR — rompe compatibilidad
  • MINOR — funcionalidad compatible
  • PATCH — corrección sin cambio de contrato

Cada liberación a producción genera un Release en GitHub con tag, notas (generadas desde los Conventional Commits) y tickets de Jira incluidos.

Anexo — Vengo de Bitbucket
