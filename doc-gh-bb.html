🚀 Migración de repositorios — Bitbucket → GitHub

🎯 Objetivo Migrar un repositorio de Bitbucket a GitHub conservando ramas, tags y PRs, limpiando previamente del historial los archivos mayores a 100 MB.
📏 Alcance Un repositorio por ejecución. No cubre migración de pipelines ni de permisos.
👤 Owner  
⏱ Duración  
🔄 Actualizado  

ℹ️ Antes de empezar

Los valores entre < > son variables que debes reemplazar. Todos los comandos se ejecutan desde PowerShell, dentro del repositorio a migrar. Repo de ejemplo: real-estate-furnishings-and-values-management.

Accesos

Herramientas

  • Check-GitLargeFiles.ps1 → I:\repos\tools\

🗺 El flujo completo

# Fase Qué pasa aquí Reversible
A📥 Preparación Clonar el repo como mirror ✅ Sí
B🔍 Diagnóstico Detectar archivos > 100 MB ✅ Sí
C💾 Respaldo Copia de seguridad del mirror ✅ Sí
D🧹 Limpieza Reescritura de historial con git filter-repo ❌ No
E🎯 Destino Solicitud y creación del repo en GitHub ✅ Sí
F🚀 Migración Push de ramas y tags ⚠️ Parcial
G🏁 Cierre Limpieza local y actualización de pipelines ❌ No

🛑 Punto de no retorno

La Fase D reescribe el historial y cambia todos los SHAs. No la ejecutes sin haber completado la copia de respaldo de la Fase C.

📥 Fase A — Preparación

A1 · Acceder al repositorio en Bitbucket

Ingresa a la URL del repo origen y confirma que tienes acceso y que es el repositorio correcto.

📷

IMAGEN — Vista del repositorio en Bitbucket

A2 · Clonar en modo mirror

git clone --mirror <url-bitbucket>/<nombre-repo>.git

ℹ️ Por qué --mirror

Baja todo: ramas, tags y referencias de PRs. Un git clone normal solo trae la rama por defecto y perderías el resto de la historia.

Resultado esperado → se crea el directorio <nombre-repo>.git (repositorio bare).

A3 · Posicionarte en el repositorio

cd I:\repos\bitbucket\<nombre-repo>.git

⚠️ Verifica el prompt

Todo lo que sigue se ejecuta dentro del repo a migrar. Correr el script desde otra ruta genera reportes vacíos y te hace creer que el repo está limpio.

🔍 Fase B — Diagnóstico de archivos grandes

B1 · Ejecutar el script de reporte

I:\repos\tools\Check-GitLargeFiles.ps1 -RepoPath . -ThresholdMB 100 -SkipBranchMapping -OutputDir .\reporte-100mb-clean
Parámetro Para qué sirve
-RepoPathRuta del repo a analizar. . = directorio actual.
-ThresholdMBUmbral en MB. GitHub rechaza blobs mayores a 100.
-SkipBranchMappingOmite el mapeo de ramas → análisis mucho más rápido.
-OutputDirCarpeta de salida del reporte HTML.

📷

IMAGEN — Salida del script en consola

  1. Los archivos que deben eliminarse del historial.
  2. Los blobs (hashes) asociados — son los que se usan en la Fase D.

💾 Fase C — Respaldo

C1 · Copia de seguridad del mirror

Duplica el mirror con otro nombre. El trabajo se sigue haciendo sobre el mirror inicial; la copia queda intacta como respaldo.

Copy-Item -Path "I:\repos\bitbucket\<nombre-repo>.git" `
          -Destination "I:\repos\bitbucket\<nombre-repo>-backup.git" `
          -Recurse

Validación → la carpeta de backup existe y pesa aproximadamente lo mismo que el original.

🚀 Fase F — Migración

F1 · Agregar el remote de GitHub

↩️ Rollback

Si falla… Qué hacer
La reescritura de historial (Fase D)
  1. Elimina el mirror corrupto.
  2. Restaura el backup de C1 y renómbralo al nombre original.
  3. Reinicia desde la Fase B.
El push a GitHub (Fase F) El repositorio origen en Bitbucket permanece intacto hasta el cierre formal. Corrige y reintenta el push.
