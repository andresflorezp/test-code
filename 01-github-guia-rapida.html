GitHub — Guía Rápida

Esta es la página que usas todos los días. Para permisos, creación de repos y gobierno: Estándares GitHub.

🔧 Configuración inicial

Solo la primera vez. Si ya tienes tu Git configurado, salta a la siguiente sección.

1. Identifícate

Esto define el nombre y correo que aparecerán en cada commit que hagas. Usa tu correo corporativo, o tus commits no se vincularán a tu usuario de GitHub.

git config --global user.name "Nombre Apellido"
git config --global user.email "nombre.apellido@empresa.com"

2. Configuración recomendada

git config --global init.defaultBranch main   # main como rama por defecto
git config --global pull.rebase true          # rebase en vez de merge al hacer pull
git config --global core.autocrlf input       # saltos de línea (usa "true" en Windows)
git config --global push.default current      # push a la rama con el mismo nombre

3. Verifica

git config --list --global

4. Habilita 2FA y SSO

En GitHub: Settings → Password and authentication → Two-factor authentication. Es obligatorio en la organización. Sin 2FA no tendrás acceso a los repos.

🖼️ Pantallazo #1: pantalla de configuración de 2FA en GitHub.

5. Configura tu acceso (SSH o Token)

Opción A — SSH (recomendado):

ssh-keygen -t ed25519 -C "nombre.apellido@empresa.com"
cat ~/.ssh/id_ed25519.pub          # copia esta salida

Pega la llave en GitHub → Settings → SSH and GPG keys → New SSH key, y autorízala para el SSO de la organización.

ssh -T git@github.com              # verifica la conexión

🖼️ Pantallazo #2: pantalla de "SSH and GPG keys" mostrando dónde pegar la llave y el botón de "Configure SSO".

Opción B — Personal Access Token:

Settings → Developer settings → Personal access tokens → Fine-grained tokens. Expiración máxima 90 días. Guárdalo en tu gestor de contraseñas, nunca en un archivo del proyecto.

🖼️ Pantallazo #3: creación de un fine-grained token con los permisos mínimos señalados.

🚀 El flujo, de principio a fin

# 1. Clona el repo (solo la primera vez)
git clone git@github.com:banamex-payments/payments-transfers-api.git
cd payments-transfers-api

# 2. Actualiza main
git checkout main && git pull

# 3. Crea tu rama (con la clave de Jira)
git checkout -b feature/PAY-1234-transfer-limits

# 4. Trabaja y haz commits pequeños
git add .
git commit -m "feat(transfers): add daily limit validation"

# 5. Sincroniza (mínimo 1 vez al día)
git fetch origin && git rebase origin/main

# 6. Publica
git push -u origin feature/PAY-1234-transfer-limits

# 7. Abre el PR en GitHub → asigna revisores → atiende comentarios

# 8. Squash and merge (cuando esté aprobado y en verde)

# 9. Limpia
git checkout main && git pull && git branch -d feature/PAY-1234-transfer-limits

💻 Comandos más usados

Clonar y empezar

git clone <url>                     # Clonar un repositorio
git clone <url> <carpeta>           # Clonar en una carpeta con otro nombre
git remote -v                       # Ver a qué remoto apunta el repo

Ver en qué voy

git status                          # Qué cambió, qué está preparado
git diff                            # Cambios que aún NO preparé
git diff --staged                   # Cambios que YA preparé
git log --oneline --graph --decorate -10   # Últimos 10 commits, visual

Preparar y confirmar (commit)

git add .                           # Preparar todos los cambios
git add <archivo>                   # Preparar un archivo específico
git add -p                          # Preparar por partes (revisas cada trozo)
git restore --staged <archivo>      # Sacar un archivo del staging

git commit -m "feat(scope): mensaje"        # Confirmar
git commit -am "fix(scope): mensaje"        # Preparar + confirmar (solo archivos ya rastreados)
git commit --amend                          # Corregir el último commit (solo si NO lo has pusheado)

Ramas

git branch                          # Ramas locales
git branch -a                       # Todas, incluidas las remotas
git checkout <rama>                 # Cambiar de rama
git checkout -b <rama-nueva>        # Crear y cambiar
git branch -d <rama>                # Borrar rama local
git push origin --delete <rama>     # Borrar rama remota

Sincronizar

git pull                            # Traer y aplicar cambios
git fetch origin                    # Traer referencias sin aplicar nada
git rebase origin/main              # Reaplicar mis commits sobre main
git push                            # Publicar
git push -u origin <rama>           # Publicar rama nueva y vincularla
git remote prune origin             # Limpiar referencias a ramas ya borradas

Guardar trabajo a medias

git stash                           # Guardar cambios sin commitear
git stash list                      # Ver lo guardado
git stash pop                       # Recuperar lo último guardado

Deshacer

git restore <archivo>               # Descartar cambios locales de un archivo
git reset --soft HEAD~1             # Deshacer último commit, conservando los cambios
git revert <hash>                   # Revertir un commit ya publicado (seguro)

⛔ Prohibido en ramas compartidas: git push --force y git reset --hard. En tu propia rama, usa git push --force-with-lease.

Tipo Cuándo
feature/ Funcionalidad nueva
bugfix/ Defecto en desarrollo
hotfix/ Defecto en producción, urgente

La clave de Jira en MAYÚSCULAS — es lo que vincula la rama al ticket automáticamente.

<tipo>(<alcance>): <qué hace, en imperativo e inglés>

✅ feat(transfers): add daily limit validation ✅ fix(auth): prevent session timeout on refresh ❌ cambios · WIP · arreglos varios v2

Tipos: feat fix refactor perf test docs build ci chore

🔀 Pull Requests

Título: [PAY-1234] feat(transfers): add daily limit validation

Antes de abrirlo:

Tamaño: menos de 400 líneas. Si es más, divídelo — un PR grande no se revisa, se aprueba.

Reglas:

  • 2 revisores mínimo · SLA de revisión: 24h hábiles
  • No apruebas tu propio PR
  • No se hace merge con checks en rojo
  • Squash and merge siempre

⛔ Las 5 reglas que no se rompen

  1. Nunca push directo a main. Todo pasa por PR, sin importar el tamaño del cambio.
  2. Una rama = un ticket de Jira.
  3. Ramas cortas. Más de 5 días vivas = el alcance está mal dimensionado.
  4. Cero secretos en el repo. Ni tokens, ni .env con valores reales, ni datos de clientes.
  5. Sincroniza a diario con main.
